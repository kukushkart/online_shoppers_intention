# Online Shoppers Intention: предсказание покупки в интернет-магазине

Бинарная классификация: закончится ли сессия посетителя покупкой (`Revenue`), по поведению в сессии (страницы, время, показатели отказов) и её контексту (месяц, тип посетителя, источник трафика). Набор данных: Online Shoppers Purchasing Intention (12 330 сессий, 17 признаков, около 15% покупок).

Все преобразования оформлены как шаги `Pipeline`, поэтому на кросс-валидации нет утечек из validation, а тест использован один раз, в самом конце.

## Почему этот датасет

Выбран потому, что на нём можно честно проверить типовые вопросы курса: сильный дисбаланс классов (метрики), заведомо коррелированные признаки (`BounceRates`/`ExitRates`, `ProductRelated`/`ProductRelated_Duration`), смесь числовых и категориальных признаков (подготовка данных) и один очень сильный признак (`PageValues`), который заставляет задуматься о надёжности результата.

## Гипотезы (сформулированы до обучения моделей)

1. **H1 (метрики).** Из-за дисбаланса accuracy вводит в заблуждение: у модели «всегда 0» accuracy выше 0.80, а у лучшей настоящей модели accuracy превышает F1-macro больше чем на 0.10.
2. **H2 (мультиколлинеарность).** Удаление признаков с |r| > 0.8 не ухудшит логистическую регрессию (изменение PR-AUC по модулю меньше 0.01).
3. **H3 (линейность).** Случайный лес обгонит логистическую регрессию по PR-AUC на тесте не меньше чем на 0.03.
4. **H4 (важность признаков).** `PageValues` будет самым важным признаком дерева, а `ExitRates` и `ProductRelated_Duration` войдут в топ-5.
5. **H5 (переобучение).** При глубине дерева больше 10: train accuracy при глубине 20 выше 0.97, а validation accuracy ниже своего максимума хотя бы на 0.02.
6. **H6 (баланс классов).** `class_weight='balanced'` повысит recall покупок не меньше чем на 0.20 ценой снижения precision.
7. **H7 (отбор признаков).** `SelectKBest` с 10 признаками не ухудшит PR-AUC логистической регрессии больше чем на 0.02.

## Результаты

Основная метрика — PR-AUC (классы несбалансированы), гиперпараметры подбирались 5-fold стратифицированной кросс-валидацией на train. Тест (2 441 сессия, 382 покупки) использован один раз.

| Модель (тест, порог 0.5) | PR-AUC | ROC-AUC | Precision | Recall | F1 |
|---|---|---|---|---|---|
| Логистическая регрессия (`log1p`, `C = 0.1`) | 0.697 | 0.922 | 0.718 | 0.600 | 0.653 |
| Решающее дерево (`max_depth = 15`, `min_samples_leaf = 50`) | 0.700 | 0.916 | 0.720 | 0.592 | 0.649 |
| **Случайный лес** (400 деревьев, `max_depth = 8`) | **0.760** | **0.936** | 0.743 | 0.620 | 0.676 |
| Случайный лес, порог 0.34 (подобран по OOF на train) | 0.760 | 0.936 | 0.645 | 0.728 | 0.684 |

Для сравнения: у модели «всегда 0» accuracy 0.844 (на CV), у леса на тесте 0.907, зато PR-AUC 0.156 против 0.760.

| № | Статус | Ключевая цифра |
|---|---|---|
| H1 | подтвердилась | accuracy 0.844 у Dummy против 0.900 у леса; PR-AUC 0.156 против 0.740 |
| H2 | подтвердилась | ΔPR-AUC = −0.0009 при std по фолдам 0.02 |
| H3 | подтвердилась | PR-AUC на тесте 0.760 против 0.697 (+0.063) |
| H4 | частично | `PageValues` — №1 (75.5% важности), но `ExitRates` на 8-м месте |
| H5 | подтвердилась (раньше, чем ожидалось) | validation accuracy 0.899 → 0.860, PR-AUC 0.690 → 0.380 |
| H6 | подтвердилась | Δrecall = +0.245, Δprecision = −0.149 |
| H7 | подтвердилась | ΔPR-AUC (10 признаков из 73) = −0.008 |

## Главные выводы

- **Accuracy здесь почти бесполезна.** Модель «всегда 0» даёт accuracy 0.844, а хороший лес 0.90. Поэтому основная метрика — PR-AUC, а для жёстких предсказаний F1 по покупкам.
- **`log1p` для скошенных признаков** улучшает логистическую регрессию с PR-AUC 0.635 до 0.683, причём на всех пяти фолдах. Подбор коэффициента регуляризации даёт всего +0.002.
- **Почти всё качество держится на `PageValues`.** Без него PR-AUC всех моделей падает с 0.68–0.76 до 0.32–0.38. Признак считается по истории покупок, поэтому в реальной системе нужно проверить, доступен ли он к моменту предсказания. Это риск, а не доказанная утечка: как именно он считается, из данных не видно.
- **Лес лучше логистической регрессии и дерева** (PR-AUC 0.760 против 0.697 и 0.700). Подобранное одиночное дерево от логистической регрессии не отличается.
- **Переобучение дерева начинается раньше глубины 10**: максимум validation PR-AUC (0.690) на глубине 5, к глубине 10 он падает до 0.506. Регуляризацией служит минимальный размер листа, а не только глубина.
- **Коррелированные признаки избыточны.** Время на страницах дублирует число просмотренных страниц; фильтр по корреляции и `SelectKBest` почти не меняют качество, но искажают важность признаков у деревьев.
- **`class_weight` и снижение порога** меняют компромисс между precision и recall, а не качество ранжирования. Порог 0.34, подобранный по out-of-fold предсказаниям, поднимает recall на тесте с 0.620 до 0.728 ценой precision (0.743 → 0.645), а F1 почти не меняется (0.676 → 0.684).
- Тест небольшой (382 покупки, одна ошибка меняет recall на 0.26 п. п.), поэтому точные значения метрик на тесте нужно читать с поправкой на шум.

## Что внутри

```
.
├── research.ipynb                    # EDA, пайплайны, модели, проверка гипотез, выводы
├── requirements.txt
├── .gitignore
└── data/
    └── online_shoppers_intention.csv # датасет (12 330 строк)
```

Ключевые элементы ноутбука:

- `make_preprocessor`: `ColumnTransformer` со стандартизацией, `log1p` (`FunctionTransformer`) и one-hot;
- сравнение моделей и подбор гиперпараметров (`GridSearchCV`, `RandomizedSearchCV`);
- отдельные эксперименты по каждой гипотезе и проверка зависимости от `PageValues`;
- подбор порога по out-of-fold предсказаниям и итоговая оценка на тесте.

## Данные

Ноутбук скачивает набор с Kaggle через `kagglehub`; копия файла также лежит в `data/online_shoppers_intention.csv`. Источники:

- Kaggle: https://www.kaggle.com/datasets/imakash3011/online-shoppers-purchasing-intention-dataset
- UCI Machine Learning Repository: https://archive.ics.uci.edu/dataset/468/online+shoppers+purchasing+intention+dataset

## Как запустить

```bash
pip install -r requirements.txt
jupyter notebook research.ipynb
```

Для скачивания данных нужен доступ в интернет. Все случайные процессы зафиксированы (`SEED = 42`), поэтому результаты воспроизводятся. Полный запуск занимает около трёх минут.
